Keysmith ships with a Forge extension adapter that handles DI registration, REST API route mounting, and database migration on startup.

## Mounting the extension

```go
import (
    "context"
    "log"

    "github.com/xraph/forge"
    grove "github.com/xraph/grove/extension"
    audithook "github.com/xraph/keysmith/audit_hook"
    "github.com/xraph/keysmith/extension"
)

// Send key lifecycle events wherever your audit trail lives.
recorder := audithook.RecorderFunc(func(ctx context.Context, ev *audithook.AuditEvent) error {
    log.Printf("keysmith audit: %s %s", ev.Action, ev.ResourceID)
    return nil
})

app := forge.NewApp(forge.AppConfig{
    Name: "billing-api",
    Extensions: []forge.Extension{
        grove.New(), // extensions.grove: driver and dsn
        extension.New(
            extension.WithHookExtension(audithook.New(recorder)),
        ),
    },
})
```

List Grove first, because Keysmith looks up the database during `Register`. Without a Grove database, pass a store yourself: `extension.WithEngineOptions(keysmith.WithStore(pgStore))`.

## What the extension does

### On registration

1. Loads config from `extensions.keysmith` (or a top-level `keysmith` key).
2. Picks a store (see [store resolution](#store-resolution-order)) and builds the `keysmith.Engine` with your engine options and hooks. It passes `keysmith.WithMetrics(app.Metrics())` ahead of your engine options, so the engine's metrics land on `/_/metrics` unless you pass a `WithMetrics` of your own. See [observability](/docs/subsystems/observability).
3. Registers the engine in the Forge DI container.
4. Mounts the REST API under `base_path` (`/keysmith` by default), unless routes are disabled.

### On start

1. Runs `Migrate` on the store, whichever backend it is, unless `disable_migrate` is set.
2. Starts the engine. It has no background work: expired keys aren't swept on a timer, so call `eng.CleanupExpiredKeys(ctx)` from your own scheduler if you want them marked expired. (`ValidateKey` refuses an expired key either way.) Each run that finds keys to expire is traced as its own root span, `expire keys`.

### On stop

Fires the `Shutdown` plugin hook. The extension doesn't close the store.

### Health

`Health` pings the store.

## REST API routes

When mounted, the extension exposes the full Keysmith REST API under the base path (so `/keysmith/v1/keys` with the defaults).

The REST API has no authentication of its own. Anyone who can reach it can create, rotate and revoke keys for any tenant they name. Put your auth middleware in front of the base path, or turn the routes off with `disable_routes` and call the engine from your own handlers.

| Method | Path | Description |
| ------ | ---- | ----------- |
| `POST` | `/v1/keys` | Create API key |
| `GET` | `/v1/keys` | List API keys |
| `GET` | `/v1/keys/:keyId` | Get API key |
| `DELETE` | `/v1/keys/:keyId` | Delete API key |
| `POST` | `/v1/keys/:keyId/rotate` | Rotate API key |
| `POST` | `/v1/keys/:keyId/revoke` | Revoke API key |
| `POST` | `/v1/keys/:keyId/suspend` | Suspend API key |
| `POST` | `/v1/keys/:keyId/reactivate` | Reactivate API key |
| `POST` | `/v1/keys/validate` | Validate raw API key |
| `POST` | `/v1/policies` | Create policy |
| `GET` | `/v1/policies` | List policies |
| `GET` | `/v1/policies/:policyId` | Get policy |
| `PUT` | `/v1/policies/:policyId` | Update policy |
| `DELETE` | `/v1/policies/:policyId` | Delete policy |

## Automatic tenant scoping

When running inside Forge, Keysmith automatically extracts the app ID and tenant ID from `forge.Scope`. No manual `WithTenant` call is needed.

## DI integration

Access the engine from the Forge DI container:

```go
eng, err := forge.Inject[*keysmith.Engine](app.Container())
if err != nil {
    log.Fatal(err)
}
```

## Grove database integration

When your Forge app uses the [Grove extension](https://github.com/xraph/grove) to manage database connections, Keysmith can automatically resolve a `grove.DB` from the DI container and construct the correct store backend based on the driver type.

### Using the default grove database

If the Grove extension registers a single database (or a default in multi-DB mode), use `WithGroveDatabase` with an empty name:

```go
ext := extension.New(
    extension.WithGroveDatabase(""),
)
```

### Using a named grove database

In multi-database setups, reference a specific database by name:

```go
ext := extension.New(
    extension.WithGroveDatabase("keysmith"),
)
```

This resolves the grove.DB named `"keysmith"` from the DI container and auto-constructs the matching store. The driver type is detected automatically, so you don't import the store packages yourself.

If the grove database is sqlite, add `_pragma=busy_timeout(5000)&_pragma=foreign_keys(1)&_txlock=immediate` to its DSN in your grove config, for example `keysmith.db?_pragma=busy_timeout(5000)&_pragma=foreign_keys(1)&_txlock=immediate`. Without them a write can fail with `SQLITE_BUSY` and `ON DELETE CASCADE` gets skipped on most connections, and keysmith logs a warning at startup when the busy timeout is missing. [Connection settings](/docs/stores/sqlite#connection-settings) explains each one.

### Store resolution order

The extension hands the engine every store it finds, and the last one wins:

1. Grove database: if `WithGroveDatabase(name)` was called (or `grove_database` is set), the named or default `grove.DB` is resolved from DI. Without either, a default `grove.DB` in the container is still picked up.
2. Explicit store: the one from `WithEngineOptions(keysmith.WithStore(s))`, used only when no grove database is found.

There is no in-memory fallback. With neither, `Register` fails with `keysmith: store is required`.

## Dashboard

Keysmith's dashboard is the React package `@forge-go/dashboard-plugin-keysmith`. It lives in the forge-dashboard repository under `packages/plugin-keysmith`, and you run it in forge's dashboard extension with the React shell. The only way it reaches keysmith is the contract contributor the extension registers in `Extension.RegisterContractContributor`. There is no Go-rendered dashboard any more, so if you're upgrading from the templ one, read [MIGRATION.md](https://github.com/xraph/keysmith/blob/main/MIGRATION.md) before you bump.

Under an auth extension that puts the session's org on the request, the dashboard shows that org. Authsome does this: its middleware sets a `forge.Scope` for the session's active org, and every page then shows that org's keys, policies, scopes and usage, the same tenant the engine already writes under. You don't configure anything for it.

`tenant_id` is the fallback for sessions without an org, and for hosts whose auth sets no Scope at all. Pass it when you build the extension:

```go
ext := extension.New(
    extension.WithDashboardTenant("acme", "billing"),
)
```

or set it in YAML:

```yaml
extensions:
  keysmith:
    dashboard:
      tenant_id: acme
      app_id: billing   # optional
```

The contract handlers try three places, in this order:

1. A `tenant_id` claim on the request's principal. No auth provider sets one today. A claim that's there but empty, or not a string, refuses on the spot and never falls through.
2. The org of the `forge.Scope` on the request. A Scope with no org (an app-only session) says nothing about the tenant, so the handlers move on.
3. `extensions.keysmith.dashboard.tenant_id`.

When none of them answers, the request gets `PERMISSION_DENIED`, and the message names `extensions.keysmith.dashboard.tenant_id`. (A request with no signed-in user stops earlier, at `UNAUTHENTICATED`.) Keysmith won't fall back to an empty tenant, because an empty tenant in a store filter matches every tenant's rows. The settings intent tells you which source it used: its `tenantSource` is `claim`, `scope` or `config`.

So on a deployment whose sessions carry orgs, a user with an active org sees that org's rows even when `tenant_id` is set, and the configured tenant only shows for sessions without one.

The dashboard takes the Scope's org as the tenant boundary for reads as well as writes, so your host must only set a `forge.Scope` from the authenticated session (as authsome does), never from anything the client sends.

`app_id` can stay empty. It only labels the rows the dashboard creates, and keysmith never filters a read by app.

When YAML and `WithDashboardTenant` both set a field, YAML wins. Each field is merged on its own, so a YAML `tenant_id` with no `app_id` still takes the app from the option.

## Extension options

| Option | Type | Default | Description |
| ------ | ---- | ------- | ----------- |
| `WithEngineOptions(opts...)` | `...keysmith.Option` | none | Engine configuration options |
| `WithHookExtension(x)` | `plugin.Plugin` | none | Register a lifecycle plugin (repeatable) |
| `WithConfig(cfg)` | `Config` | defaults | Override default extension configuration |
| `WithLogger(l)` | `log.Logger` (go-utils) | the extension's Forge logger | Set the logger the engine uses |
| `WithDisableRoutes()` | none | `false` | Skip HTTP route registration |
| `WithDisableMigrate()` | none | `false` | Skip migrations on Start |
| `WithBasePath(path)` | `string` | `"/keysmith"` | URL prefix for keysmith routes |
| `WithGroveDatabase(name)` | `string` | `""` | Named grove.DB to resolve from DI |
| `WithRequireConfig(b)` | `bool` | `false` | Require config in YAML files |
| `WithDashboardTenant(tenantID, appID)` | `string, string` | `"", ""` | Tenant the dashboard uses for a session with no org, and an optional app that labels rows it creates. A YAML value wins |

## File-based configuration (YAML)

When running as a Forge extension, Keysmith automatically loads configuration from YAML config files. The extension looks for config under the following keys (in order):

1. `extensions.keysmith`, the standard Forge extension config namespace
2. `keysmith`, a top-level shorthand

### Example

```yaml
# forge.yaml
extensions:
  keysmith:
    disable_routes: false
    disable_migrate: false
    base_path: "/keysmith"
    grove_database: ""
    dashboard:
      tenant_id: "acme"
      app_id: ""
```

### Config fields

| YAML Key | Type | Default | Description |
|----------|------|---------|-------------|
| `disable_routes` | `bool` | `false` | Skip HTTP route registration |
| `disable_migrate` | `bool` | `false` | Skip migrations on Start |
| `base_path` | `string` | `"/keysmith"` | URL prefix for all routes (empty also means `/keysmith`) |
| `grove_database` | `string` | `""` | Named grove.DB from DI |
| `dashboard.tenant_id` | `string` | `""` | Tenant the dashboard uses for a session with no org. Leave it empty and those requests answer `PERMISSION_DENIED` |
| `dashboard.app_id` | `string` | `""` | Labels rows the dashboard creates. Optional, and never filters a read |

### Merge behaviour

File-based configuration is merged with programmatic options. Programmatic boolean flags (`DisableRoutes`, `DisableMigrate`) always win when set to `true`. For other fields, YAML values take precedence, then programmatic values, then defaults. That holds for `dashboard.tenant_id` and `dashboard.app_id` one field at a time.
