---
title: MongoDB Store
description: MongoDB store for document-oriented and horizontally-scalable deployments.
---

The `store/mongo` package implements Keysmith's `store.Store` interface using the grove ORM with the MongoDB driver. It stores keys, policies, scopes, usage records, and rotations as documents, making it a natural fit for deployments that already run MongoDB.

## Usage

```go
import (
    "github.com/xraph/grove"
    "github.com/xraph/grove/drivers/mongodriver"
    "github.com/xraph/keysmith/store/mongo"
)

db, err := grove.Open(mongodriver.Open("mongodb://localhost:27017", "keysmith"))
if err != nil {
    log.Fatal(err)
}

s := mongo.New(db)
if err := s.Migrate(ctx); err != nil {
    log.Fatal(err)
}

eng, err := keysmith.NewEngine(keysmith.WithStore(s))
```

## Migrations

`Store.Migrate` builds Keysmith's indexes, and that's all it does. A collection that doesn't exist yet gets created along the way, without schema validation, and none of the versioned migrations run (see Grove migrations below). Call it on startup:

```go
if err := s.Migrate(ctx); err != nil {
    log.Fatal(err)
}
```

It builds indexes on six collections:

| Collection | Description |
| ---------- | ----------- |
| `keysmith_keys` | API keys with hash, state, and metadata |
| `keysmith_policies` | Policy definitions |
| `keysmith_scopes` | Scope definitions |
| `keysmith_key_scopes` | Key-scope junction table |
| `keysmith_usage` | Per-request usage records |
| `keysmith_rotations` | Rotation history records |

Building an index that already exists is a no-op, so you can run it on every startup. That includes the stable-sort indexes on `keysmith_usage` and `keysmith_rotations`, `{tenant_id, created_at, _id}` and `{key_id, created_at, _id}`, which the Usage and Rotations lists page by.

## Internals

| Aspect | Detail |
|--------|--------|
| Driver | grove ORM + mongodriver |
| Migrations | `Store.Migrate` builds indexes; `Migrations` (a grove group) creates collections and runs the versioned changes |
| Transactions | None: the store runs no multi-document transactions |
| Concurrency | MongoDB native concurrency model |
| Subsystems | keys, policies, scopes, usages, rotations |

## Grove migrations

Collection creation and every versioned change live in the exported `Migrations` group, and they only run when you hand that group to grove's migration orchestrator. `Store.Migrate` never runs them. The group:

- creates each collection with JSON Schema validation generated from the grove model structs, plus its indexes
- adds the `old_key_hash` index on rotations (`20260930000001`)
- drops `keysmith_usage_agg`, which nothing ever wrote to (`20260930000002`)
- closes the grace windows of rotations recorded before the grace fix (`20260930000003`)
- adds the stable-sort indexes on usage and rotations (`20261005000001`)

If you only call `Store.Migrate` on a database that predates these, an old empty `keysmith_usage_agg` collection stays. It's harmless. The engine also refuses the old grace windows whether or not the migration ran.

```go
import mongostore "github.com/xraph/keysmith/store/mongo"

// mongostore.Migrations is a migrate.Group for the keysmith mongo store.
// Register it with the grove migration orchestrator for coordinated migrations.
```

## When to use

| Scenario | Recommended |
| -------- | ----------- |
| Document-oriented workloads | Yes |
| Horizontally-scaled environments | Yes |
| Teams already running MongoDB | Yes |
| Single-node development | Possible, though SQLite may be simpler |
| Maximum SQL compatibility | No, use PostgreSQL |
